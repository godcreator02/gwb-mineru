**本页回答**：`src/index.ts` 管什么、不管什么；一条作业怎么走过六个状态、每一步写进作业账什么；`submit` 返回前做了什么；
outDir 的占用与覆盖怎么管；作业账怎么写；失败怎么记、`recover` 怎么补。它跟外面各插件的连接见[首页](/docs)的接缝 ①–⑧，
注入与 peer 汇总在[插件之间怎么连](/docs/wiring)。

作业机管作业的一生：检查参数、占住 outDir、写账、立即返回；后台为每条作业调云端客户端与解包；每次状态推进都写账；
到终态推事件；启动时对账；卸载时打断；凭归档重新解包。它不知道 MinerU 的接口长什么样（在[云端客户端](/docs/mineru-client)），
不知道 zip 里有什么、怎么防越界（在[解包](/docs/extract)），也不知道调用方拿产物做什么。

## submit 返回前做了什么

MinerU 解析一篇要几十秒到几分钟，命令是调用方等着回执的一次调用，所以云端那部分一律放到后台。`submit` 在返回前只做本地的事：
检查整批参数、占住每个 outDir、等启动对账完成、把 `queued` 写进作业账。写账也在返回前做完，是因为回了作业号就要保证宿主重启后还查得到；
写不进去就撤回这批作业、整批拒绝。

{/* ref file="../plugins/mineru/src/index.ts" lines="221-240" hash="96643e5d3194" blob="995921077508" */}

## 一个 outDir 同一时间只归一条作业

占用发生在第一个 `await` 之前：两个同时到来的 `submit` 不能都看到「这个 outDir 空着」。先把整批查完再一起占，所以有一条冲突就一个都不占。
同一批里两条指向同一个目录，与遇上一条还在跑的作业，报错分开写，并写出占着它的作业号。作业到终态就放开这个 outDir：

{/* ref file="../plugins/mineru/src/index.ts" lines="310-332" hash="15b24757b3fd" blob="96ba44422c60" */}

outDir 已经存在时，它必须是目录；里面有东西而这一项没带 `overwrite`，提交时就拒，不排一条最后注定失败的作业。
这只是提前检查：云端跑的几分钟里谁都可能往 outDir 里放东西，真正说了算的是解包的[提交点](/docs/extract)。

## 作业各自独立，同时跑

一次交 N 篇就是 N 个独立的单文件云端任务，各自申请上传位、上传、轮询、下载，谁先完谁先写账。不合进一个云端批：三个文件合进一个批全部解析失败，
把失败的拆成独立任务重新提交，两个都成功；5 个独立任务同时跑，5 个都成功。数据与取舍见轨迹卡[全并行](/trajectory/2026-09-18-parallel-and-serial-overturned)。

## 失败只记账；recover 在本地补解包

解包那一步失败（围栏拒了某条 entry、提交时 outDir 被占、磁盘读写出错）时，作业记成 `failed`，账上写着归档路径。
`recover` 用这份归档重走解包：不申请上传位、不上传、不轮询、不花额度。没走到下载就失败的作业账上没有归档，`recover` 直接拒。
`recover` 只是把本地没做完的那一步做完，不是对云端的重试：

## 作业账的写法

新作业入列、每次状态推进、云端进度变化都会重写整张作业账。几条作业同时推进时，同一个 `jobs` 文档被并发改名，在 Windows 上报过
`EPERM` / `ENOENT`，所以写盘排成一条链，每次写的是轮到那一刻的整张账。写失败不抛（后台的作业还在跑），只记下最近一次错误，

## 启动对账与卸载打断：只标记，不重跑

启动时读回作业账，上次没到终态的作业（包括还没开始的）标成 `interrupted`，原因写进 `error`；插件卸载时中止还在跑的请求，
没到终态的一并标上。不丢账、不假装还在跑，也不自动重新提交：

## 轮询的三个数

5 秒问一次；云端在解析时，状态与已解析页数 10 分钟不动判停滞；连排队在内 1 小时判超时。怎么判在云端客户端，数值是作业机定的：
长文档与低优先级排队不能被一个短的墙钟误判为失败（误判的代价是调用方重新提交、同样的页数再扣一次额度），卡死的也不能无限等。
取舍见轨迹卡[看进度判超时](/trajectory/2026-09-17-poll-by-progress)。

## 用到的服务从提供方上下文取

方法里的 `this.ctx` 是调用方的上下文。作业用到的定时器、写账、清理都登记在插件自己的上下文 `providerContext` 上，
调用方卸载带不走一条还在跑的转换。命令总线、设置、数据三个服务写在 `static inject` 里，缺一个插件就不加载，比加载之后缺一部分功能好查；

## 怎么测

仓根 `pnpm check`（插件包里先构建，再 `vitest run`）。这一层由 `tests/job-runner.test.mjs` 覆盖：真 cordis 上下文，
设置、数据、命令总线三个替身服务加一个替身内核；云端是换掉的全局 `fetch`（申请上传位、上传、轮询、下载都在内存里，不联网、不花额度），
PDF 是随手写的假文件。它证明四件事：一条作业走完全过程、回执字段齐全；同一 outDir 的三种拒绝（同批冲突、前一条在跑、前一条已完成但目录非空）；
显式覆盖时旧产物整个进备份；提交点冲突后 `recover` 凭归档补上，而且云端一次都没再问。四条命令的处理函数没有测试。

## 代码地图

- **在哪**：`plugins/mineru/src/index.ts`，一个文件
- **先读**：`GwbPdf2mdApi`（对外接口）→ `submit` → `runFullChain` → `recover`
- **读序**：`[Service.init]`（登记命令与设置、启动对账）→ `submit`（`newQueuedJobs` → `claimOutDirs` →
  `assertSubmissionsAcceptable` → `enterJobsIntoLedger`，再逐条 `startInBackground`）→
  `runFullChain`（`uploadToCloud` → `pollCloudResult` → `downloadAndExtractOrSettleFailed`）→
  `recover`（凭归档重解）→ `recordCloudProgress`（进度写账）→ `updateJobAndPersist`（状态推进、终态事件）→
  `writeLedger` / `loadLedgerMarkingLeftoversInterrupted`（写账与启动对账）
- **可跳过**：`dist/`（构建产物：esbuild 输出 js、tsc 输出类型声明）、`describeErrorWithCause`（把 `cause` 拼进失败原因的几行）、
  `extractOptionsFor` / `jobFieldsFromExtractResult`（把作业记录转成解包参数、再把解包结果转回作业字段）
