# 作业机：gwbPdf2md 服务

**本页回答**：`src/index.ts` 管什么、不管什么；submit 怎么收一批、作业为什么各自独立跑、
outDir 的占用与覆盖怎么管；账怎么记；三个邻居服务为什么是硬依赖。

## 管什么

作业的一生：验参占位秒回、各跑各的全链（报名 → 上传 → 轮询 → 下载解包）、每步推进落账、
云端进度变了记账、终态推 UI 事件、启动对账、卸载打断、凭盘上归档重新解包。outDir 的占用与
覆盖策略也在这一层。`pdf2md.*` 四条命令与说明书注册同样在这儿。

## 不知道什么

- 不知道 MinerU API 长什么样——三个动作在 [云端客户端](/docs/mineru-client)
- 不知道 zip 里有什么、怎么防越界、怎么原子落盘——在[解包与语言](/docs/extract)
- 不知道调用方拿产出干什么——零库概念，「归档副本、成品位命名」那套篇目录布局是调用方的
  私有约定，不在这儿
- 不知道 token 的值——settings 给，submit 时现取

## 数据结构

一条作业的账，落盘就是它——只装可序列化的东西。产物那几个字段（`markdown` / `lang` / `files` /
`skipped`）与归档、提交结果（`archive` / `commit` / `backup`）都是 done 之后才有的：

{/* ref file="../plugins/mineru/src/index.ts" lines="48-86" hash="d73d7e30809a" blob="c497a02950a2" */}

`state` 六态：`queued → uploading → running → done | failed | interrupted`，后三态是终态。
`queued` 是落账到开跑之间的瞬态。`progress` 是云端报来的已解析页 / 总页，`running` 期间才会
出现，done 时补满；云端排队时没有它。

## 提供的接口

- 服务 `ctx.gwbPdf2md`：`submit` / `recover` / `get` / `list`（契约见[用法](/docs/usage)）
- 命令 `pdf2md.submit` / `pdf2md.status` / `pdf2md.jobs` / `pdf2md.recover`
- 事件 `job-settled`（终态时，经内核 emit 通道）
- 说明书目录 `skills/`（经 gwb-skills 局部注入）

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |

| `gwbData` | 作业账 `writeDoc` / `readDoc`（文档名 `jobs`） | gwb-data 插件 | 同上（内存 Map） |

## 怎么单独测

`pnpm test`（先 `pnpm build`，再 `node --test "tests/*.test.mjs"`）。打这一层的是
`tests/job-runner.test.mjs`：真 cordis Context + 三个假邻居服务（settings / data / commands）+
假内核，云端是替身 fetch（报名、PUT、轮询、下载四个动作全在内存里，零网络零额度），PDF 是随手
写的假文件。它证明四点：一条作业的全链与回执字段；同一 outDir 的三种拒法（同批撞车、
前一条在跑、前一条已 done 但目录非空）；显式覆盖时旧产物整份进备份；提交点撞车后
`pdf2md.recover` 凭归档补上且**云端一次都没再问**。

能单测的两块被刻意切在服务外面——云端客户端与解包都是纯函数模块，不依赖 cordis，
这正是依赖方向单向带来的好处。

## 代码地图

- **在哪**：`src/index.ts`，一个文件
- **先读**：文件头注释（14–35 行，自我介绍与 outDir 那条线）→ `submit`（262 行）→ `run`（419 行）→ `recover`（341 行）
- **读序**：`[Service.init]`（登记命令与设置、启动对账）→ `submit`（整批验参、占位、落账、逐条启动）→
  `start`（处理 run 自己抛出的异常，把作业记成 failed）→ `run`（一条作业的全链）→ `extract`（下载解包那一段与失败时的归档记账）→
  `recover`（凭归档重解）→ `noteProgress`（进度记账）→ `finish`（状态推进 + 终态 emit）→
  `persist` / `load`（账的排队写与对账）

  `extractOptions` / `extractReceipt`（把作业记录转成解包参数、再把解包结果转回作业字段）

## 设计点（错了难改的那几条）

**submit 秒回是判据不是偏好**：命令是页面等着的一次调用，分钟级的云端解析绝不能在线等——
作业号数组先回，成败看 status。秒回的边界在「云端」：本地验参与**把 queued 落进作业账**
仍在线等（毫秒级）——回了作业号就是「跨重启查得到」的承诺，账落不了盘整批拒、撤回入列：

{/* ref file="../plugins/mineru/src/index.ts" lines="14-17" hash="10b6a3f15ee9" blob="2b641c5eaaa3" */}

**一个 outDir 一次只落一个作业**：占位发生在**第一个 await 之前**（两个并发 submit 不能都验到
「这个 outDir 空着」），占位失败整批当场拒、一条账都不落、云端一次都不问。同批里两条瞄着同一个
目录、或撞上还在跑的作业，报的话分别说清是哪种，并点名是谁占着。到终态就放掉这一格：
下一份产物可以进来，那一关归「已有产物」管：

{/* ref file="../plugins/mineru/src/index.ts" lines="260-331" hash="fdf1ee42d4a0" blob="c497a02950a2" */}

**已有产物要显式覆盖**：outDir 不是目录、或里面已经有东西而这条没带 `overwrite`——提交阶段就拒
（不排一条注定在提交点失败的作业）；提交点还会再查一遍，那才是权威的（本地验完到云端跑完隔着
分钟级，中间谁都可能往里放东西）。覆盖时旧产物整份进工作根备份，作业账上记 `commit` 与
`backup`，回执里说得清这次是什么结果：

{/* ref file="../plugins/mineru/src/index.ts" lines="386-405" hash="8424337e37b6" blob="c497a02950a2" */}

**作业各自独立、全并行，不聚合进一个云端批**：一次 submit 的 N 篇就是 N 个独立的单文件任务，
报名、上传、轮询、下载各跑各的，谁先完谁先落账。两件事都有实测背书——云端对并发单任务
零挑剔（5 路全并发 5/5 过），而把多文件**聚合进一个 batch_id** 会连带解析失败（同样的文件
聚合 3/3 挂、拆开 2/2 过），判据见[那张卡](/trajectory/2026-09-18-parallel-and-serial-overturned)：

{/* ref file="../plugins/mineru/src/index.ts" lines="407-415" hash="d348580a8739" blob="c497a02950a2" */}

**失败只管记账，重解包那扇门在本地**：解包那一段失败（围栏拒、提交点撞车、盘上 I/O）时，作业落
`failed` 并**把归档路径记进账**——云端那份结果已经在盘上了，`pdf2md.recover` 凭它重走一遍解包链，
不重新报名、不上传、不轮询、不再花额度。没走到下载就失败的（云端解析失败、轮询超时）账上没有
归档，recover 会直说无路可走。**两件事都不动六态的含义**：recover 是把本地没走完的那一步走完，
不是对云端的重试：

{/* ref file="../plugins/mineru/src/index.ts" lines="339-370" hash="01c8ed935462" blob="c497a02950a2" */}

**作业账写盘排队**：进度、状态推进、新作业入账都会触发写盘，多作业并行推进时同一个 `jobs`
文档并发 rename 在 Windows 上 `EPERM` / `ENOENT`。写盘挂到一条链上，每次写轮到那一刻的整张账——
这是并行世界里唯一保留下来的串行：

{/* ref file="../plugins/mineru/src/index.ts" lines="501-514" hash="e691487b8996" blob="c497a02950a2" */}

**失败原因带上 cause**：`fetch` 失败时 `String(err)` 只有一句 `TypeError: fetch failed`，
真原因（`ECONNRESET`、连接超时）在 `err.cause` 里——拼进作业的 `error` 与日志。mineru.net 的
连接偶发抖动与并发无关（单发也撞、重试即过），防护靠如实记账，不靠限流：

{/* ref file="../plugins/mineru/src/index.ts" lines="137-145" hash="a9fbf3ebcce2" blob="c497a02950a2" */}

**作业用到的资源登记在提供方，不登记在消费者**：方法里的 `this.ctx` 是消费者的——定时器、记账、清理
全部经 `this.own`，消费者卸载不该带走一个还在跑的转换（上面「依赖的接口」那段引用过）。

**启动对账与卸载打断，只标不重跑**：重启后上次留下的非终态作业（含还没启动的）标 `interrupted`
（理由写进 error），插件卸载时 abort 还在跑的控制器、把非终态一并标上——不丢账、不假装还在跑，
也**不**自动重提：

{/* ref file="../plugins/mineru/src/index.ts" lines="516-538" hash="327dbc18e866" blob="c497a02950a2" */}

**进度只记账，不推事件**：轮询每 5 秒一问，云端报的页数变了才写盘，没变不写；界面事件仍只有
落定那一条 `job-settled`——看进度的人查 status，插件不把每一轮回包转发成事件：

{/* ref file="../plugins/mineru/src/index.ts" lines="468-477" hash="3be4049b8777" blob="c497a02950a2" */}

**轮询的三个数定在这层**：5 秒一问、云端干活时进度停滞 10 分钟判失败、连云端排队总上限
1 小时。怎么判停滞在[云端客户端](/docs/mineru-client)；数值是作业机的取舍——长文档与低优先级
排队不该被墙钟误杀（误杀的代价是调用方重提、同一份页数再扣一次额度），卡死的也不该无限等。
作业各跑各的，谁也不占谁的轮询上限：

{/* ref file="../plugins/mineru/src/index.ts" lines="41-44" hash="f16737aea7af" blob="c497a02950a2" */}

**设置项必须在 init 里 define**：不声明的话 get 永远回 undefined——实机撞过一轮，症状是
「token 明明在 settings.json 里，命令却报没配」（见[那面墙](/trajectory/2026-09-08-wall-rewrite-drops)）。
