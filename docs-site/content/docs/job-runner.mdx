# 作业机：gwbPdf2md 服务

**本页回答**：`src/index.ts` 管什么、不管什么；submit 怎么收一批、作业为什么各自独立跑、
账怎么落；三个邻居服务为什么是硬依赖。

## 管什么

作业的一生：验参落账秒回、各跑各的全链（报名 → 上传 → 轮询 → 解包）、每步推进落账、
云端进度变了记账、终态推 UI 事件、启动对账、卸载打断。命令面 `pdf2md.*` 三条与说明书注册也在这层。

## 不知道什么

- 不知道 MinerU API 长什么样——三个动作在 [云端客户端](/docs/mineru-client)
- 不知道 zip 里有什么、markdown 怎么认——在 [解包与语言](/docs/extract)
- 不知道调用方拿产出干什么——零库概念，「归档副本、成品位命名」那套篇目录布局是调用方的
  私有约定，不在这儿
- 不知道 token 的值——settings 给，submit 时现取

`state` 六态：`queued → uploading → running → done | failed | interrupted`，后三态是终态。
`queued` 是落账到开跑之间的瞬态。`progress` 是云端报来的已解析页 / 总页，`running` 期间才会
出现，done 时补满；云端排队时没有它。

## 提供的接口

- 服务 `ctx.gwbPdf2md`：`submit` / `get` / `list`（契约见[用法](/docs/usage)）
- 命令 `pdf2md.submit` / `pdf2md.status` / `pdf2md.jobs`
- 事件 `job-settled`（终态时，经内核 emit 通道）
- 说明书目录 `skills/`（经 gwb-skills 局部注入）

## 怎么单独测

仓里没有单测设施，现状两条：`pnpm typecheck` 守类型；真链路进隔离 home 实跑（要真 token、
真云端——`devkit.home.new` 开 home、`plugin-manager.install` 装件、`devkit.dev` 换开发版、
`settings.set` 填 token）。实跑记录：全链与进度在 `probes/2609172224_poll-and-live-run/`，
数组并行提交在 `probes/2609181525_parallel-submit/`（一次交 3 篇、同时在跑峰值 3、坏路径
整批拒）；批与并行的云端行为判据在 `probes/2609181430_batch-parallel/`。
能单测的两块被刻意切在服务外面——云端客户端与解包都是纯函数模块，不欠 cordis，
这正是依赖方向单向的回报。

## 设计点（错了难改的那几条）

**submit 秒回是判据不是偏好**：命令是页面等着的一次调用，分钟级的云端解析绝不能在线等——
作业号数组先回，成败看 status。秒回的边界在「云端」：本地验参与**把 queued 落进作业账**
仍在线等（毫秒级）——回了作业号就是「跨重启查得到」的承诺，账落不了盘整批拒、撤回入列：

{/* ref file="../src/index.ts" lines="15-21" */}

**作业各自独立、全并行，不聚合进一个云端批**：一次 submit 的 N 篇就是 N 个独立的单文件任务，
报名、上传、轮询、下载各跑各的，谁先完谁先落账。两件事都有实测背书——云端对并发单任务
零挑剔（5 路全并发 5/5 过），而把多文件**聚合进一个 batch_id** 会连带解析失败（同样的文件
聚合 3/3 挂、拆开 2/2 过），判据见[那张卡](/trajectory/2026-09-18-parallel-and-serial-overturned)：

{/* ref file="../src/index.ts" lines="194-230" */}

{/* ref file="../src/index.ts" lines="246-254" */}

**作业账写盘排队**：进度、状态推进、新作业入账都会触发写盘，多作业并行推进时同一个 `jobs`
文档并发 rename 在 Windows 上 `EPERM` / `ENOENT`。写盘挂到一条链上，每次写轮到那一刻的整张账——
这是并行世界里唯一保留下来的串行：

{/* ref file="../src/index.ts" lines="324-338" */}

**失败原因带上 cause**：`fetch` 失败时 `String(err)` 只有一句 `TypeError: fetch failed`，
真原因（`ECONNRESET`、连接超时）在 `err.cause` 里——拼进作业的 `error` 与日志。mineru.net 的
连接偶发抖动与并发无关（单发也撞、重试即过），防护靠如实记账，不靠限流：

{/* ref file="../src/index.ts" lines="97-104" */}

**作业的命脉挂提供方，不挂消费者**：方法里的 `this.ctx` 是消费者的——定时器、落账、收尾
全挂 `this.own`，消费者卸载不该带走一个还在跑的转换（上面「依赖的接口」那段钉过）。

**启动对账与卸载打断，只标不重跑**：重启后上次留下的非终态作业（含还没点火的）标 `interrupted`
（理由写进 error），件卸载时 abort 还在跑的控制器、把非终态一并标上——不丢账、不假装还在跑，
也**不**自动重提：

{/* ref file="../src/index.ts" lines="340-362" */}

**进度只记账，不推事件**：轮询每 5 秒一问，云端报的页数变了才写盘，没变不写；界面事件仍只有
落定那一条 `job-settled`——看进度的人查 status，件不把每一轮回包转发成事件：

{/* ref file="../src/index.ts" lines="293-303" */}

**轮询的三个数定在这层**：5 秒一问、云端干活时进度停滞 10 分钟判失败、连云端排队总上限
1 小时。怎么判停滞在[云端客户端](/docs/mineru-client)；数值是作业机的取舍——长文档与低优先级
排队不该被墙钟误杀（误杀的代价是调用方重提、同一份页数再扣一次额度），卡死的也不该无限等。
作业各跑各的，谁也不占谁的轮询上限：

{/* ref file="../src/index.ts" lines="39-42" */}

**设置项必须在 init 里 define**：不声明的话 get 永远回 undefined——实机撞过一轮，症状是
「token 明明在 settings.json 里，命令却报没配」（见[那面墙](/trajectory/2026-09-08-wall-rewrite-drops)）。
