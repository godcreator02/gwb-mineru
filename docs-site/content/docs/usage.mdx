# 用法：把 PDF 变成 markdown

**本页回答**：现在的代码怎么用——消费方代码怎么 inject、agent 走哪四条命令、token 配在哪、
产出长什么样、outDir 已有东西时怎么办、失败了怎么处置。

## 两种调用方式，同一套作业

- **消费方（代码）**：`inject: ['gwbPdf2md']`，拿 `ctx.gwbPdf2md` 四方法——`submit(files)`
  （一作业一文件的数组）/ `recover(id)` / `get(id)` / `list()`

{/* ref file="../plugins/mineru/src/index.ts" lines="63-81" hash="30a9d392839b" blob="c1ea4e1b5397" */}

- **agent（命令）**：`pdf2md.submit` / `pdf2md.status` / `pdf2md.jobs` / `pdf2md.recover` 四条，
  「一个孤立 PDF 想要 markdown」走这边；gwb-paper-fetch 的说明书也让 agent 直接调 `pdf2md.submit`
  转论文

## submit 收数组、秒回，作业各自独立同时跑

**返回不是完成。** MinerU 云端解析是分钟级的，而命令是页面等着的一次调用——所以作业号
数组先回、后台各跑各的，终态经 `pdf2md.status` 查、或等 `job-settled` 事件。一次交几篇，
几篇就**同时**在跑（云端一个任务一个任务地转，互不排队）——`pdf2md.jobs` 里看到多条
`running` 是常态。验参是整批验：数组里有一条坏形状（路径不绝对、文件不在、超 200MB），
**整批当场拒**，不落半批账；token 没配也是当场挡，不排出注定失败的作业。**作业账落不了盘
（数据盘满等）同样整批拒**——回了作业号就是「跨重启查得到」的承诺，兑现不了就不回。
`job-settled` 事件也在账落盘之后才发。

轮询 5 秒一问；云端解析中页数 10 分钟不动、或连云端排队 1 小时没完，结算为 `failed`
（error 说明是停滞还是超时）。解析中的作业带 `progress`（已解析页 / 总页），云端排队时没有它。

done 的作业带三样产出：`markdown`（outDir 里那份完整 markdown 的文件名，通常是 `full.md`）、
`lang`（zh/en，按 CJK 占比判）、`files`（落盘清单）。正文里的图是 `images/xxx` 相对链接，
跟 md 同层，不用改。账上另有三个字段交代「怎么落盘的」：`commit`（`created` 新建 / `replaced` 覆盖）、
`backup`（覆盖时旧产物挪去的备份目录）、`skipped`（zip 里没搬的那些杂项，如 `layout.json`）。

## 一个 outDir 一次只落一个作业；已有产物要显式覆盖

**一个 outDir 同一时间只归一条作业**。同一批里两条瞄着同一个 outDir、或撞上一条还在跑的
作业，整批当场拒（报错里点名是谁占着），云端一次都不问——两条作业并排往同一个目录里解，先落定的
那条账立刻就不准了。

**outDir 里已经有东西时默认拒**（提交阶段就拒，不排一条注定在提交点失败的作业）。要覆盖就在这一项
上显式写 `"overwrite": true`：旧产物**整份**先挪进 outDir 同级工作根的 `backup-<时间戳>/`，再上新的
——备份不自动清，那是调用方的东西。产物是**整份出现**的：解包在工作根的 staging 里做完、最后一步
rename 进 outDir，中途失败时 outDir 还是上一版（或还没出现），没有新旧混着这种状态。

`outDir` 不存在也可以交——它不再被预先建出来，第一份产物落位那一刻它才出现。

```json
{ "files": [{ "input": "D:/papers/xxx.pdf", "outDir": "D:/papers/xxx", "overwrite": true }] }
```

## 归档与 recover：解包失败不必重花额度

结果 zip 一抓下来就先在工作根（outDir 同级的 `.<outDir 名>.pdf2md/`，文件名 `archive-<作业号>.zip`）
留一份，再解包。所以解包那一段失败时（围栏拒掉可疑条目、提交点撞上别人刚占位、盘上 I/O 出错），
作业落 `failed` 但**账上记着归档路径**——`pdf2md.recover { "id": "<作业号>" }` 凭它把解包链重走一遍：
零云端、零额度，不重新报名、不上传、不轮询。归档一直留着，直到调用方自己把工作根删掉。

recover 只对 `failed` / `interrupted` 的作业有效；`done` 的（产物已经在 outDir 里）与还在跑的会被
挡回来。账上没有 `archive` 的（上传或轮询阶段就失败的）也会直说无路可走——那种要结果只能重新
submit，会再花一次额度。

## token 缺席当场挡，token 失效写进 error

设置节 `mineru`、键 `token`（secret），在 mineru.net 的 API 管理页创建；没配时 submit 报一句
「MinerU token 没配」：

{/* ref file="../plugins/mineru/src/index.ts" lines="221-224" hash="cb433e5de77d" blob="c1ea4e1b5397" */}

配置命令：`settings.set { "section": "mineru", "key": "token", "value": "…" }`。值是 secret，
status 与日志里永远看不到它。token 是**现取现读**的——settings 改值不用重新加载插件。

配了但无效或过期的 token submit 挡不住（要问云端才知道），作业会在几秒内 `failed`，error 里带
`code=A0211` 与换 token 的那句话；换完重提即可。

## 事件与终态

作业落定时经内核 emit 通道推一条事件（`source: "gwb-mineru"`、`type: "job-settled"`、载荷带
jobId / ok / outDir / error）。**事件是给看着界面的人的，不是给 agent 的回执**——agent 照样
轮询 `pdf2md.status`。

## 坑四条

- **`interrupted`**：宿主重启或插件卸载把作业打断了，账上如实标注。MinerU 侧可能其实做完了，但
  结果没人取——重提一次作业就是了（同一个 PDF 再 submit 一遍），没有恢复续跑
- **失败原因看 `error`**：上传失败、解析失败、停滞或超时、zip 结构不对、云端业务错，都在那个字段里，
  日志里也有同一句。认得出的云端错误码（token 失效、超 200MB、超 200 页、当天任务数到顶）附一句
  照着就能做的话；网络层失败（`fetch failed`）括号里带真原因（`ECONNRESET` 之类）——mineru.net
  的连接偶发抖动与并发无关（单发也撞、重试即过），看到它重提就好
- **outDir 已有产物 / outDir 被占**：报「outDir 里已经有 N 项东西」就是没带 `overwrite`；
  报「正被作业 X 占着」就是那条还在跑，等它落定或换个目录。两条都不动盘上的东西
- **files 里每一项都得是两个绝对路径**：`input` 得是存在的文件、不超过 200MB；`outDir` 不必预先建，
  第一份产物落位那一刻它才整份出现。submit 当场验，验不过整批抛错不落账

说明书（给 agent 的那份）在包内 `skills/pdf2md/SKILL.md`，经 gwb-skills 插件登记；没装 gwb-skills
的 home 里作业机照常加载——skills 是局部可选注入。
