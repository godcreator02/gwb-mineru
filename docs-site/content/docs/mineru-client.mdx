**本页回答**：跟 MinerU 云端的三次交互各自怎么走；什么算终态、什么算停滞；停滞与超时为什么记成 `failed` 而不是抛错；
回包里的错误怎么认。它在系统里的位置是[首页](/docs)的接缝 ⑦ 与 ⑨。

这个模块只认调用方递进来的 token 与 batchId：不知道作业、作业账与作业号（进度交给 `onProgress` 之后怎么记是[作业机](/docs/job-runner)的事），
不知道 token 从哪来，也不知道结果怎么写到磁盘上（拿到 `full_zip_url` 之后是[解包](/docs/extract)的事）。它只用全局 `fetch`、`AbortSignal`
与 `node:fs` 读文件，不依赖 gwb 与 cordis。

## 三次交互

`requestUpload` 申请上传位，回 `[batchId, uploadUrl]`；`upload` 把 PDF 原样 `PUT` 到预签名地址（不带 `Content-Type`，接口规格如此）；
`poll` 反复问解析结果，直到终态。另外导出判定 `isDone`、错误类型 `MineruError` 与单文件上限 `MAX_FILE_BYTES`（200MB，作业机在
`submit` 时先在本地挡）。

{/* ref file="../plugins/mineru/src/core/mineru.ts" lines="51-84" hash="2a597c33a3ec" blob="8aab970ebcb2" */}

MinerU 这组接口收的是「一批多个文件」，这里一条作业一个文件，`files` 数组长度恒为 1。并行靠同时跑多个独立任务，不靠合批：
三个文件合进一个批全部解析失败，拆开重交就成功，见轨迹卡[全并行](/trajectory/2026-09-18-parallel-and-serial-overturned)。

## 轮询：停滞与超时记成 failed

轮询的节奏、停滞上限、总上限、进度回调与中止信号都由调用方给：

{/* ref file="../plugins/mineru/src/core/mineru.ts" lines="86-97" hash="a5863ffb53b4" blob="8aab970ebcb2" */}

判失败分两道。云端在解析（`running` / `converting`）时，状态与已解析页数一段时间都不动才算停滞；排队（`waiting-file` / `pending`）
不判停滞，排多久是云端额度与优先级的事，只受连排队在内的总上限管。两种都不是异常，是这次解析的一种结局：回一份 `state: 'failed'`
的结果，`err_msg` 写明是停滞还是超时，并提醒云端可能还在跑：

## 先认回包，再认状态码

token 错时 MinerU 回 HTTP 401，错误码的键叫 `msgCode`；任务不存在之类回 HTTP 200，键叫 `code`。只看状态码会把 token 错变成一句
「HTTP 401」，所以先认回包：`code` 或 `msgCode` 不是 0 就抛 `MineruError`，认不出回包的非 2xx 才报 HTTP 错。两种回包的形状实测见
`probes/2609172223_api-error-shapes/`。

## 怎么测

这个模块没有直接的单测。`tests/job-runner.test.mjs` 换掉全局 `fetch`，从作业机那一侧走过三次交互，但替身第一次轮询就回终态，
所以排队不判停滞、解析中页数不动判停滞、总上限这几条判断没有单测；它们的证据在 `probes/2609172224_poll-and-live-run/`
（冻结的输入与不依赖任何包的脚本）。真云端要真 token，只在 `probes/` 的实验里跑过。
