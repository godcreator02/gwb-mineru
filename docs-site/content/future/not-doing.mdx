# 刻意不做什么

下面每一条都是**决定不做**，不是排期没排到。要做，得先推翻写出它的那条理由。
写下来是为了防一年后有人看到「缺了个自动化」顺手补上，理由充分，然后再来几次。

## 自动重试与恢复

作业 `failed` 或 `interrupted` 之后，件不做任何重提。MinerU 侧可能其实做完了，但结果没人
取——处置就是同一个 PDF 再 submit 一遍。

为什么：重试策略是调用方的私事（重试几次、间隔多久、要不要先查 MinerU 侧状态，各家不同）。
件替调用方定策略，等于把「要不要再花一次分钟级解析」的决定权从用的人手里拿走。失败原因
如实写进作业的 `error`，日志里同一句——够调用方自己决定了。

## 并发上限与排队调度

`submit` 来几个跑几个，没有并发上限、没有队列调度（`queued` 只是落账到开跑之间的瞬态）。

为什么：这个件的调用方是件不是人——papers 转一批论文要多少路并发，是 papers 的账。云端
配额也是调用方 token 自带的那份。件里设上限，等于替所有调用方猜一个安全值。

## 结果缓存与去重

同一个 PDF 提交两次，就完整跑两遍全链，不做内容哈希去重、不做结果缓存。

为什么：outDir 是调用方给的，产出归属调用方目录；件里存第二份就是长出「库」的概念——
恰好是零库概念划掉的边界。真要省这笔解析费，调用方自己知道自己转过什么。

## 引擎抽象层

只有 MinerU，没有「转换引擎」接口。件名就是引擎名。

为什么：第二个引擎出现之前，「引擎」这个词在本件没有指涉。名不对应那个例外（引擎命名）
已经把「换引擎」的语义边界划出来了——真有第二个引擎那天，该讨论的是件怎么拆，不是先
做空插槽。了断背景见[那张卡](/trajectory/2026-09-08-engine-vs-function-naming)。

## 进度事件与云端状态镜像

云端报来的已解析页 / 总页记在作业的 `progress` 上，status 查得到；但**不推进度事件**，事件
只有落定那一条 `job-settled`；云端的细分状态（`waiting-file` / `pending` / `converting`）也
不上作业账，作业仍是六态。

为什么：看进度的人本来就在查 status，每 5 秒一轮的回包转发成事件，界面收一串噪音；把云端
的状态原样搬上作业账，等于把件的命令面变成云端 API 的镜像——云端哪天改状态名，调用方跟着
改。页数是云端给的事实、作业机记下来即可，状态机是件自己的契约。进度数据怎么来的见
[那张卡](/trajectory/2026-09-17-poll-by-progress)。

## Agent 轻量解析 API 与云端回调

MinerU 另有一套免 token 的 Agent 轻量 API（`/api/v1/agent/`），精准解析 API 也支持
`callback` 推结果。两样都不接。

为什么：轻量 API 限 10MB / 20 页、只回一个 markdown 的 CDN 链接，图不落 `images/`——交出去的
三样对不上，论文也大多超限。回调要云端能打进来，这个件只在本机跑，进不来；轮询够用。

## 论文库的任何概念

不认识 papers、不做归档副本、不做成品位命名、不做翻译与规格化——出 outDir 之后的每一步
都是调用方的事。

为什么：这些是 papers 的私有约定，进了本件就成了两个件共用一份私约——papers 改布局本件
跟着改。本件交原料：markdown 文件名、lang、文件清单，就三样。
