# gwb-mineru 是什么

gwb 内核线（单元 `26090705ymz`）的 **MinerU 转换件**：提供 `pdf2md` 服务——PDF 经 MinerU
云端转 markdown。零库概念：输入一个 PDF 绝对路径、一个输出目录，产出完整 markdown +
`images/` 原样落 outDir。

## 为什么是作业，不是命令

MinerU 云端解析是**分钟级**的，而 gwb 的命令是页面等着的一次调用（单进程线上没有超时红线
了，但「页面等着」的性质没变）。所以这个件是作业机：`submit` 秒回作业号，后台跑全链，终态
经事件推、经 status 查。这个取舍写进了代码的头注释，也定下了整个件的形状。

## 名不对应：件名说引擎，服务名说功能

件叫 `gwb-mineru`（谁在干活：MinerU 引擎），服务与命令叫 `pdf2md`（干什么：转换）。对着
gwb 线「服务名跟件名走」的惯例，这是唯一一个有意例外——消费方 inject 的永远是 `gwbPdf2md`。
了断见[那张卡](/trajectory/2026-09-08-engine-vs-function-naming)。曾用包名
`@godcreator/gwb-pdf2md` 0.0.1–0.0.3 已废弃。

## 零库：papers 在调用侧

papers（单元 `26090814ifd`）在**它自己的代码里**注入 `gwbPdf2md` 做论文转换——归档副本、
成品位命名那套篇目录布局是 papers 的私有约定，不进这个件。agent 不直接碰 papers；本件
`pdf2md.submit` 命令是「一个孤立 PDF 想要 markdown」的那扇门。

MinerU 客户端与 zip 解包的接口规格沿用老仓 god-papers（单元 `26082116etw`，只作参考）；
语言判定（CJK 占比）是通用文本分析，跟着这个件走。

## 当前阶段

0.4.0 发 gitea 个人源，跟着内核 0.1 契约走（单进程线）。这个件没有浏览器半、没有窗格——
纯 node 半的作业机，内核契约变了它多半不用动（迁 0.1 那次只改了一句注释，见[路线](/future/roadmap)）。
会让它动的是**云端 API 本身**：0.2.0 是对齐现行文档的一轮，0.4.0 的续取是顺着「结果留存有时限」
这个实测事实补的门；下一次多半也是云端改了什么。
