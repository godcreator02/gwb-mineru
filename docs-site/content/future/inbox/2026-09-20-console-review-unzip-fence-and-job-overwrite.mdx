### GWB-31 已完成输出被后续作业覆盖，失败只留半份结果（P0｜读码推断）
* 位置：`src/index.ts:197-215,266-273`、`src/core/extract.ts:51-75`
* 现象：submit 接受同批多作业同一 outDir、接受目录已有文件；作业全并行；解包逐文件 writeFile 原地覆盖；ZIP 内存解析不存可恢复副本。同 outDir 两个 PDF 互相覆盖、先 done 的账指向被后一个修改的目录；中途 I/O 错留下新旧混合文件且无原始 ZIP 可重解
* 期望：每作业独占 staging + 持久化原始归档，完整校验/解包后原子提交；拒绝并发占用同一输出目标；覆盖现有产物定显式策略与可恢复版本；归档恢复与重新云端提交分开

### GWB-32 卸载取消不能贯穿请求，interrupted 可被继续运行覆盖（P1｜已验证预先 abort 的 poll 仍完成；卸载竞态为读码推断）
* 位置：`src/index.ts:134-136,235-277,347-355`、`src/core/mineru.ts:65-95,119-140,148-159`、`src/core/extract.ts:49`
* 现象：controller.signal 只传入轮询 sleep，不传 upload/poll/download 各 fetch；sleep 不查 signal.aborted。卸载先记 interrupted，后台 catch 不区分 AbortError 又记 failed；未被取消的下载还可记 done——热卸载完成不意味着作业停止
* 期望：同一取消信号与请求超时 signal 合并贯穿所有 I/O；每次 await 后检查终态/代际；sleep 清监听并处理已 abort；卸载返回前等实际关闭和最终持久化；取消用独立终态，不归因云端失败。**公开作业/取消服务改动需拍板**

### GWB-33 声称「落完账才返回」，实际返回与终态事件均不等持久化（P1｜已验证：未完成的 writeDoc 替身）——✅ 已修 @gwb-mineru 9f7432c（2026-09-20，未发版）
* 位置：`src/index.ts:73-75,214-216,292-320,184-186,324-341`
* 现象：submit 和 finish 都 `void persist()`；persist 捕获写失败只告警继续；初始化 load 也未 await——命令注册即可提交，整表写入可能先于旧账载入（覆盖旧记录）。用户拿到的 job id 未必跨重启可查
* 期望：初始账本载入作服务 ready 前提；submit 在云端动作前确认 queued 落盘；终态事件在输出和终态账本持久化后发布；不可恢复的写入失败对调用方可见
